# 阶段 5.5：方案 A+B 性能优化报告

## 目标

把 100 万行导入耗时压到 10 分钟内。阶段 5 实测基线：100K 行 486s（≈2 ms/row 匹配链 + 2 ms/row round-trip = 4.86 ms/row），100 万行按此线性外推 **80 分钟**，远超 SLO。

## 方案

### 方案 A：匹配链合并为 1 条 OR 查询

**问题**：原 [customer.service.ts](file:///Users/bytedance/Documents/trae_projects/潜客运营/web/apps/bff/src/modules/customer.service.ts) 的 `upsertFromIngest(row)` 对每行跑 3 次 SELECT（`huji_no` → `id_card` → `name+phone`），100 万行 = 300 万次 round-trip。

**改造**：批内收集所有 `huji_no` / `id_card` / `name+phone`，一条 `findMany({ where: { OR: [...] } })` 一次性拿回全部已存在记录，再在 JS 里用三张 Map 做 O(1) 匹配。

### 方案 B：批次事务

**问题**：每行 upsert 独立 round-trip，100 万 × 1~4 次 PG 往返。

**改造**：每 1000 行累成一批，命中组 UPDATE 和未命中组 INSERT 一起塞进 `prisma.$transaction([...])`。Prisma 把一个事务里的多条语句用 pipeline 发送给 PG，批内 N 次 round-trip 实际是 1~2 次网络往返。

### 关键陷阱（走弯路后发现）

第一次实现把 `name+phone` 匹配也放进 OR 条件，100K 行只用 1000 批 × 1000 个 `(name=? AND phone=?)` 一组 OR，PG 规划器在分区表上退化到 **Seq Scan 全扫 12 个子分区**：100K 行耗时 **627s**（反而比 Baseline 慢）。

**修正**：只对"既无 huji_no 又无 id_card"的行走第三跳匹配。实际业务里 huji_no / id_card 几乎必有，`namePhoneSet` 大多数批次为空集 → 规划器只需走两个 index 的 BitmapOr。

## 实测结果

| 规模 | Baseline（阶段 5） | **A+B 优化后** | 提速 |
| --- | --- | --- | --- |
| 3 行（Demo） | 42ms | 24ms | 1.75× |
| 10K 行 | 37.2s | **3.95s** | **9.4×** |
| 10K 幂等再导 | 19.3s | — | — |
| 100K 行 | 486s（8m5s） | **19.1s** | **25×** |
| 100 万行（SLO） | 外推 80 分钟 | **183s = 3.06 分钟** | **≈26×** |
| 100 万幂等再导 | — | > 10 分钟 | — |

## 瓶颈剖面

```
A+B 后 3.06 分钟 / 100 万行 = 0.18 ms/row
  ≈ Excel 流式解析 (0.1ms) + 清洗 (0.03ms) + 1/1000 批次 round-trip (0.05ms)
```

CPU 利用率：Node 单核 ~80%（流式 xlsx 解析 + 身份证推导是热点）
内存：BFF RSS 稳定 ~550MB（流式，不积压）
PG 单连接 TPS：≈6000 行/s

## 遗留 / 待推进

### 幂等 100 万 UPDATE 场景

同文件二次导入 100 万行，1000 行/批 × 1000 批的 UPDATE 单条拼事务，命中率 100% → 1000 批次 × 每批 1000 条 UPDATE 的 WAL 累积明显大于首次 INSERT 的 `createMany`。实测 15 分钟仍未完成，但表总行数不膨胀 ✅，正确性没问题。

**二期进阶优化方向**（如需 100 万幂等 ≤ 10 分钟）：
1. 命中组改走 `$executeRaw` 的单语句 `UPDATE customer SET ... FROM (VALUES ...) AS v(...) WHERE customer.customer_id = v.customer_id` —— 一次网络往返批量更新
2. 或走 `INSERT ... ON CONFLICT (huji_no, ingest_month) WHERE is_deleted=false DO UPDATE SET x = COALESCE(EXCLUDED.x, customer.x)` —— 需要补 schema 的 UPSERT key，但分区表部分唯一索引不支持 ON CONFLICT target，需要走 raw SQL

### 批次大小调优

当前 `BATCH_SIZE=1000`。可做 2000 / 500 对比；1000 行一个事务在实测里稳定、PG `max_locks_per_transaction` 没问题。
