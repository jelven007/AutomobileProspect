## 4. 性能瓶颈定位

```
实测 4.86 ms/row
     ≈ PG 本地 round-trip (1ms) × 3~4 次
     = SELECT by huji_no + SELECT by id_card + SELECT by name+phone + INSERT
```

**瓶颈不在 Prisma / Node，而在"匹配链 3 次 SELECT + 1 次 INSERT 的 round-trip 数"。**

- CPU：Node 单核 ~15%
- 内存：BFF RSS 稳定在 ~450MB（流式 xlsx，不积压）
- PG：单连接单条 upsert，TPS 200~500

## 5. 二期性能优化方向（供排期）

| 方案 | 预期提速 | 复杂度 |
| --- | --- | --- |
| **A. 匹配链合并为 1 条 CTE** `WITH m AS (SELECT customer_id FROM customer WHERE (huji_no=$1 AND huji_no<>'') OR id_card=$2 OR (name=$3 AND phone_masked=$4) LIMIT 1) ...` | 3~4× | 低 |
| **B. 每批 1000 行走 `prisma.$transaction`** | 2~3× | 低 |
| **C. 匿名记录（无 huji_no/id_card）走 `COPY FROM STDIN`** | 10~20× | 中 |
| **D. ingest-service 直写 PG，BFF 只做 CRUD** | 一次性批写 1 千万 | 中 |
| **E. Doris + Bitmap 支撑秒级人群圈选（二期架构目标）** | 跨业务线复用 | 高 |

推荐一期收尾只做 A+B（约半天工），直接把 100 万行压到 10 分钟内，再启动二期。
