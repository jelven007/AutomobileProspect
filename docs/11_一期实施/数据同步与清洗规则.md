## 3. 清洗 Pipeline（固化在代码中）

```ts
// 伪代码：pipeline 顺序执行；关键是"身份证明文仅在 enrich 环节使用，入库前统一脱敏"
const pipeline = [
  dropColumns([1, 3, -1, -2]),                       // Rule 1-3
  mapColumn(4, stripPrefixDigits('2016户籍统计')),    // Rule 4
  trimAllStrings(),
  mapColumn(2, parseDateTime()),                     // stat_time
  mapColumn(5, parseDate()),                         // birth_date（Excel 原值）
  mapColumn(6, mapGenderToCode()),                   // 原列若有则直接用
  // 身份证列先不脱敏，暂存明文
  stashIdCardPlain(7, { field: 'id_card_raw' }),
  mapColumn(9, maskPhoneMid4()),
  // enrich：从身份证明文派生 province / city / birth_date / gender
  enrichFromIdCard({
    source: 'id_card_raw',
    rules: {
      province: 'first_2',               // 身份证前 2 位 → 省
      city:     'first_4_lookup',        // 身份证前 4 位 → 市（有映射表时）
      birth_date: 'yyyyMMdd_7_14',       // 身份证 7-14 位 → 出生日期
      gender:   'seq_17',                // 身份证第 17 位 奇/偶 → M/F
    },
    overwrite: false,                    // 原列有值时不覆盖
  }),
  // enrich 结束，统一脱敏并丢弃明文
  maskIdCard(from='id_card_raw', to='id_card'),
  dropField('id_card_raw'),
  requireColumns(['name', 'huji_no']),
  dropRowIf((r) => !/^\d+$/.test(r.huji_no)),
];
```

### 3.1 `stripPrefixDigits`

```ts
export const stripPrefixDigits = (prefix: string) => (v: unknown) => {
  if (v == null) return '';
  const s = String(v).trim();
  const stripped = s.startsWith(prefix) ? s.slice(prefix.length) : s;
  return stripped.replace(/\D/g, '');
};
```

| 输入 | 输出 |
|---|---|
| `"2016户籍统计9161337"` | `"9161337"` |
| `"2016户籍统计 9161337"` | `"9161337"` |
| `"9161337"` | `"9161337"` |
| `"2016户籍统计ABC-123-456"` | `"123456"` |
| `""` / `null` | `""` → 整行被丢弃 |

### 3.2 `maskIdCard`

```ts
export const maskIdCard = () => (v: unknown) => {
  if (v == null) return '';
  const s = String(v).replace(/\s+/g, '');
  if (!/^\d{17}[\dXx]$/.test(s)) return s;      // 非合规保持原文，由告警路径处理
  return `${s.slice(0, 6)}********${s.slice(-4)}`;
};
```

### 3.3 `parseDateTime`

- 优先匹配 `yyyy/mm/dd HH:mm:ss`
- 兼容 `yyyy-mm-dd HH:mm:ss`、Excel 日期序列号
- 转为 UTC 入库，减少跨时区歧义

### 3.4 身份证派生 `parseIdCard`

| 推导字段 | 来源 | 规则 | 说明 |
|---|---|---|---|
| `province` | 前 2 位 | 查 GB2260 一级码表（34 条） | 100% 可推 |
| `city` | 前 4 位 | 先查 `cities`（现行 ~340 条），再 fallback 到 `cities_historical`（历史编码别名 ~25 条） | 覆盖主流身份证签发码 |
| `district` | 前 6 位 | 查 `districts`（直辖市 + 省会 + 一线城市区县，共 ~340 条） | 可通过 `setExtraDistrictCodes` 扩展 |
| `birth_date` | 7–14 位 | `yyyyMMdd` → `yyyy-mm-dd` | 100% 可推 |
| `gender` | 第 17 位 | 奇=M / 偶=F | 100% 可推 |

**码表存储**：`web/apps/ingest-service/configs/gb2260.json`，模块懒加载缓存，热更新调用 `_resetGb2260Cache()`。

**历史编码兼容**：Demo.xlsx 中的 `5102xx` 等已撤销区划码也能命中（走 `cities_historical`），保留"身份证签发时的真实归属"。

**覆盖策略**：`overwrite=false`。Excel 原列若已有真值，派生结果不覆盖；原列为空或 `gender='U'` 时才回填。

**校验位**：对第 18 位做 ISO 7064 Mod 11-2 校验，返回 `checksum_valid` 字段。校验失败不丢弃，建议上游在 `ingest_row_log` 中以 `id_card_checksum_invalid` 记录供运营抽检。

**保留的人工维护位**：`occupation`、`education`、`marital_status` 由身份证推不出，一期保留表字段但不自动填充，可通过客户详情页 / Admin API 维护。

## 4. 去重策略（**本次重点**）

> 单一 xlsx 内可能存在重复编码号；多个 xlsx 之间也会有重合。去重分三层：

### 4.1 层 1：文件内 Map 去重

- 组件：`RowDeduper`（内置于 `ingest-service`）
- 主键：`dedupe.key = huji_no`
- 策略：`keep = last`（同一编码号出现多次时，保留文件靠后的那条，视为更新）
- 开销：仅存一份 `CustomerRow` 的内存副本，百万行约 300 MB，可控

### 4.2 层 2：跨批次 UPSERT

- 由 `sink` 侧执行：

```sql
INSERT INTO customer (huji_no, name, gender, birth_date, id_card, phone_masked,
                      address, stat_time, source_file, source_row, ingest_batch)
VALUES (...)
ON CONFLICT (huji_no) DO UPDATE
SET name         = EXCLUDED.name,
    gender       = EXCLUDED.gender,
    birth_date   = EXCLUDED.birth_date,
    id_card      = EXCLUDED.id_card,
    phone_masked = EXCLUDED.phone_masked,
    address      = EXCLUDED.address,
    stat_time    = EXCLUDED.stat_time,
    source_file  = EXCLUDED.source_file,
    source_row   = EXCLUDED.source_row,
    ingest_batch = EXCLUDED.ingest_batch,
    version      = customer.version + 1,
    updated_at   = NOW()
WHERE customer.is_deleted = FALSE;
```

- 唯一索引：`uk_customer_huji ON customer (huji_no) WHERE is_deleted = FALSE`
- 效果：重跑同一文件、或多个文件涉及相同编码号时，表体不会膨胀，`version` 自增用于审计

### 4.3 层 3：疑似冲突告警（身份证）

- 现象：**编码号不同，但身份证相同** → 可能是手工录入错误或家庭成员误填
- 策略:
  - 不丢弃，仍按编码号主键入库
  - `RowDeduper` 维护 `bySecondary: Map<id_card, first_seen_huji_no>`
  - 冲突时写入 `warnings[]`，在 `CustomerImportReport.conflict_warnings` 中返回
  - BFF 把前 100 条冲突追加到 `errors`，供前端表格展示

### 4.4 去重统计字段

`CustomerImportReport`：

| 字段 | 含义 |
|---|---|
| `total_rows` | xlsx 原始行数 |
| `success_rows` | 清洗通过（**去重前**） |
| `duplicate_rows` | 文件内被覆盖的重复行数 |
| `written_rows` | 实际落到 PG 的行数（≈ `success_rows - duplicate_rows`） |
| `skipped_rows` | 清洗失败（编码号非数字、必填缺失等） |
| `conflict_warnings` | 身份证冲突明细列表 |

## 5. 流水线架构

```
对象存储(xlsx)
   │  (list objects + 分片)
   ▼
┌──────────────────┐
│ ingest-worker    │  Node.js + exceljs 流式解析，不全加载
└──┬───────────────┘
   │ Row 流
   ▼
┌──────────────────┐
│ cleaning         │  dropColumns → stripPrefix → maskIdCard → validate
└──┬───────────────┘
   │ Clean Row
   ▼
┌──────────────────┐
│ RowDeduper       │  文件内 huji_no 去重（keep=last）
│                  │  身份证冲突 → warnings
└──┬───────────────┘
   │ Deduped Row
   ▼
┌──────────────────┐
│ sink             │  Batch 2000 → PG UPSERT (ON CONFLICT huji_no)
└──┬───────────────┘
   ▼
customer 表 (按 ingest_month 分区)
+ ingest_job（文件级，含 duplicate_rows/written_rows/warnings）
+ ingest_row_log（异常级 + 冲突级）
```

## 6. 表结构（PostgreSQL）

```sql
CREATE TABLE customer (
  customer_id    BIGINT PRIMARY KEY,
  huji_no        VARCHAR(32)  NOT NULL,
  name           VARCHAR(64)  NOT NULL,
  gender         CHAR(1),
  birth_date     DATE,
  id_card        VARCHAR(32),         -- 已脱敏存储
  phone_masked   VARCHAR(16),
  address        VARCHAR(256),
  stat_time      TIMESTAMPTZ,
  province       VARCHAR(32),         -- 由身份证前 2 位推导
  city           VARCHAR(64),         -- 由身份证前 4 位推导
  district       VARCHAR(64),         -- 预留；人工或 GB2260 补全
  occupation     VARCHAR(64),         -- 人工维护位
  education      VARCHAR(32),         -- 人工维护位
  marital_status VARCHAR(16),         -- 人工维护位
  source_file    VARCHAR(256),
  source_row     INT,
  ingest_batch   VARCHAR(64),
  ingest_month   DATE  NOT NULL,
  version        INT   NOT NULL DEFAULT 1,
  is_deleted     BOOLEAN NOT NULL DEFAULT FALSE,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (ingest_month);

CREATE UNIQUE INDEX uk_customer_huji ON customer (huji_no) WHERE is_deleted = FALSE;
CREATE INDEX idx_customer_address_trgm ON customer USING gin (address gin_trgm_ops);
CREATE INDEX idx_customer_name_trgm    ON customer USING gin (name gin_trgm_ops);
CREATE INDEX idx_customer_id_card      ON customer (id_card);
CREATE INDEX idx_customer_province     ON customer (province);
CREATE INDEX idx_customer_city         ON customer (city);

CREATE TABLE ingest_job (
  job_id          VARCHAR(64) PRIMARY KEY,
  source_bucket   VARCHAR(128),
  source_prefix   VARCHAR(256),
  status          VARCHAR(16) NOT NULL,
  total_rows      BIGINT DEFAULT 0,
  success_rows    BIGINT DEFAULT 0,
  skipped_rows    BIGINT DEFAULT 0,
  duplicate_rows  BIGINT DEFAULT 0,
  written_rows    BIGINT DEFAULT 0,
  warnings        BIGINT DEFAULT 0,
  started_at      TIMESTAMPTZ,
  finished_at     TIMESTAMPTZ,
  error           TEXT
);

CREATE TABLE ingest_row_log (
  job_id      VARCHAR(64),
  file        VARCHAR(256),
  row_no      INT,
  reason      VARCHAR(64),      -- cleaning_error / id_card_conflict / huji_duplicate
  raw         JSONB
);
```

## 7. 幂等与一致性

- **行级幂等**：`INSERT ... ON CONFLICT (huji_no) DO UPDATE`，自然去重 + `version` 自增
- **文件级幂等**：`ingest_job.job_id = sha256(bucket + prefix + file_etag)`；重跑同 ETag 文件 → 行级 UPSERT 覆盖后 `written_rows` 不变、`duplicate_rows` 增量
- **冲突不阻断**：身份证冲突仅告警入 `ingest_row_log`，不影响批次提交

## 8. 性能预算

| 单文件 | 行数 | 预估耗时 | 内存 |
|---|---|---|---|
| 100 MB | 100 万 | 60–80 s | 350 MB（含 Deduper Map） |
| 1 GB | 1000 万 | 12 min | 500 MB |
| 全量（亿级） | 100M | ≤ 4 h（8 worker 分片） | 单 worker ≤ 600 MB |

关键点：
- 流式读 xlsx（禁止 `XLSX.read(file, {type:'buffer'})` 全加载）
- `RowDeduper` 的 Map 大小 = 文件内不重复行数，百万级 OK；若单文件超千万需开启"分块文件 + 多 worker"模式
- 批量写 PG，批大小 2000；进程级 N worker 分片不同文件，避免同 `huji_no` 跨 worker 争抢

## 9. 调度与运维

- 一期用 **系统 cron**：每天 02:00 扫 `huji/{yesterday}/` 下的新文件
- 失败重试 3 次，之后告警（企微 webhook）
- `ingest_job.warnings > 0` 时在"同步任务"页标红，提示运营核实身份证冲突

## 10. 配置样例

```yaml
# configs/ingest-schema.yaml
source:
  type: s3
  bucket: ${INGEST_BUCKET}
  prefix: huji/
  endpoint: ${S3_ENDPOINT}

parse:
  skip_header_rows: 1
  sheet: 0

columns:
  drop_indexes: [1, 3, -1, -2]
  mappings:
    - { index: 2, field: stat_time,   transform: parse_datetime }
    - { index: 4, field: huji_no,     required: true,
        transform: strip_prefix_digits, transform_args: ["2016户籍统计"] }
    - { index: 5, field: birth_date,  transform: parse_date }
    - { index: 6, field: gender,      transform: map_gender }
    - { index: 7, field: id_card,     transform: mask_id_card }   # 延迟脱敏，enrich 后执行
    - { index: 8, field: name,        required: true }
    - { index: 9, field: phone_masked, transform: mask_phone_mid4 }
    - { index: 10, field: address }

# 身份证派生，enrich 在 mapping 之后、mask_id_card 之前执行
enrich:
  from_id_card:
    source_field: id_card              # 清洗期临时持有明文
    fill:
      province: first_2
      city: first_4_lookup
      birth_date: yyyyMMdd_7_14
      gender: seq_17
    overwrite: false
    extra_city_codes: ${EXTRA_CITY_CODES_FILE}   # 可选：补入完整 GB2260 市级码表

dedupe:
  key: huji_no
  keep: last
  secondary_key_warn: id_card          # 编码号不同但身份证相同 → warning
  cross_batch:
    strategy: upsert
    on_conflict: update                 # 幂等覆盖，version +1

sink:
  type: postgres
  table: customer
  batch_size: 2000
  conflict_key: huji_no
```
