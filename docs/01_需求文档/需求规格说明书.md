# 需求规格说明书（SRS）

> 文档编号：SRS-LeadOps-001　　版本：v1.0　　日期：2026-10-04　　负责人：张路

## 1. 文档说明

### 1.1 目的
明确汽车行业潜客运营系统（下文简称"系统"或"平台"）的业务目标、用户角色、功能需求与非功能需求，作为后续产品、设计、研发、测试、运营的共同依据。

### 1.2 适用范围
覆盖整车厂与经销商集团的潜在客户管理、意向挖掘、运营触达与经营洞察。不含售后维保、二手车交易撮合、整车 OTA。

### 1.3 术语
| 术语 | 含义 |
|---|---|
| 潜客 | 尚未成交的潜在购车客户 |
| OneID | 跨渠道用户唯一标识 |
| 意向分 | 购车意愿量化分值（0–100） |
| L0–L5 | 意向等级，L5 最高 |
| SDR | Sales Development Representative，销售开发代表 |
| MA | Marketing Automation，营销自动化 |
| MTA | Multi-Touch Attribution，多触点归因 |
| DMP | Data Management Platform |
| CDP | Customer Data Platform |

## 2. 业务背景

### 2.1 现状痛点
- 用户数据分散（对象存储、CRM、广告、埋点、门店 POS），缺统一视图。
- 亿级潜客规模，缺乏高性能人群圈选，运营凭经验，命中率低。
- SDR 外呼无优先级指引，无效呼叫高，到店率低。
- 多通道触达缺少频控与归因，用户体验差、ROI 不透明。
- 隐私合规压力大，缺乏字段级权限与审计机制。

### 2.2 业务目标
| 维度 | 指标 | 目标值（上线 6 个月内） |
|---|---|---|
| 规模 | 画像用户数 | ≥ 1 亿 |
| 规模 | 日行为事件 | ≥ 10 亿条 |
| 性能 | 人群圈选 P95 | ≤ 3 秒 |
| 性能 | 画像点查 P99 | ≤ 50 ms |
| 业务 | 高意向识别准确率 | ≥ 70% |
| 业务 | SDR 有效外呼率 | +50% |
| 业务 | 线索转化率 | +30% |
| 业务 | 单线索运营成本 | -25% |

### 2.3 非目标
- 不替换现有 DMS/CRM，只做对接与反哺。
- 不做售后、维保、金融核心系统。

## 4. 功能需求

### 4.1 需求优先级定义
- **P0 必须（MVP 必备）**
- **P1 重要（上线后 3 个月内）**
- **P2 增强（6 个月内）**
- **P3 远期**

### 4.2 功能列表

#### FR-01 数据接入　P0
- FR-01-01 支持对象存储（S3/OSS/TOS）批量接入，分区 `dt/channel`。
- FR-01-02 支持 CRM MySQL Binlog CDC 接入。
- FR-01-03 支持 App/Web 埋点流式接入（Kafka）。
- FR-01-04 支持广告平台 API 拉取（巨量、腾讯、广点通）。
- FR-01-05 数据质量规则：空值率、重复率、取值范围、新鲜度。
- FR-01-06 失败自动重试，死信队列可追查。

#### FR-02 OneID 身份打通　P0
- FR-02-01 强字段合并：手机号 MD5、身份证哈希。
- FR-02-02 弱字段合并：设备 ID + IP + UA 概率匹配。
- FR-02-03 支持手动合并与拆分回滚，操作留痕。
- FR-02-04 合并事件下发至 Kafka 供下游订阅。

#### FR-03 标签与画像　P0
- FR-03-01 三层标签：基础属性、行为意向、模型预测。
- FR-03-02 标签申请 → 审核 → 上线 → 下线流程。
- FR-03-03 标签血缘（标签 → 特征 → 原始表）。
- FR-03-04 画像 360 视图点查（基础 + 标签 + 行为 + 分数）。
- FR-03-05 批量画像查询（单次 ≤ 500 OneID）。

#### FR-04 AI 意向挖掘　P0 / P1
- FR-04-01 规则意向分（P0，兜底）。
- FR-04-02 ML 意向评分 L0–L5（P1）。
- FR-04-03 车型偏好推荐 Top-N（P1）。
- FR-04-04 价格带预测（P2）。
- FR-04-05 流失/休眠预警（P2）。
- FR-04-06 Lookalike 相似人群扩量（P2）。

#### FR-05 人群圈选　P0
- FR-05-01 可视化拖拽构造条件（AND/OR/NOT、嵌套、时间窗）。
- FR-05-02 秒级预估人数。
- FR-05-03 异步导出名单（Redis Set / CSV / DMP 直推）。
- FR-05-04 SQL 兜底查询。
- FR-05-05 人群列表、复用、下线。

#### FR-06 旅程编排与触达　P0 / P1
- FR-06-01 DAG 编排（发送、等待、条件、分流、Webhook、派单）。
- FR-06-02 多通道：短信、企微、外呼、App Push、EDM、广告 DMP。
- FR-06-03 频控（用户 × 通道 × 7 天）。
- FR-06-04 A/B 实验分流。
- FR-06-05 发送回执、点击、到店回传。
- FR-06-06 退订管理。

#### FR-07 SDR 派单与跟进　P1
- FR-07-01 智能派单（意向 × 地域 × 产能 × 历史成交率）。
- FR-07-02 24h 未跟进自动回收。
- FR-07-03 销售工作台：客户 360、推荐话术、跟进记录。
- FR-07-04 跟进状态回传驱动模型。

#### FR-08 洞察与分析　P1
- FR-08-01 实时经营大屏（10s 刷新）。
- FR-08-02 转化漏斗（曝光→点击→留资→到店→试驾→成交）。
- FR-08-03 MTA 多触点归因（Shapley / 时间衰减）。
- FR-08-04 自助 BI（Superset）。
- FR-08-05 战区/城市/门店/销售下钻。

#### FR-09 权限与审计　P0
- FR-09-01 RBAC + 数据域（战区、门店、车型）。
- FR-09-02 字段级权限（PII 脱敏）。
- FR-09-03 操作审计日志（180 天留存）。
- FR-09-04 告知同意、退订、PII 加密、二次审批导出。

#### FR-10 平台管理　P1
- FR-10-01 数据源、Schema、DQC 规则管理。
- FR-10-02 模型版本管理与灰度。
- FR-10-03 任务监控、重跑、告警订阅。
- FR-10-04 Webhook 事件订阅。

## 5. 非功能需求（NFR）

| 维度 | 要求 |
|---|---|
| 性能 | 圈选 P95 ≤ 3s；点查 P99 ≤ 50ms；实时打分 P99 ≤ 100ms |
| 可用性 | 核心服务 99.9%，点查 99.95% |
| 规模 | 1 亿用户、10 亿事件/日，3 年支持 10 倍增长 |
| 一致性 | 批流一致，线上线下特征差异 ≤ 1% |
| 安全 | 全链路 TLS 1.3；KMS 托管；PII 加密 |
| 合规 | 符合《个人信息保护法》《数据安全法》 |
| 可观测 | 全链路 Trace + 指标 + 日志 |
| 可维护 | 模块化、灰度发布、一键回滚 |
| 国际化 | 一期中文，二期支持多语言 |
| 浏览器 | Chrome/Edge 最近 2 版，Safari 最近 2 版 |

## 6. 关键用户故事（User Story）

- **US-01 市场运营**：作为市场运营，我希望按"L5 高意向 + 一线城市 + 近 30 天留资"圈选人群并秒级看到人数，以便快速决定投放素材。
- **US-02 SDR**：作为 SDR，我希望每天上班打开工作台就看到今日高意向线索池并有推荐话术，以便高效外呼。
- **US-03 店长**：作为 4S 店店长，我希望看到辖区当日线索/到店/成交漏斗，以便复盘与排班。
- **US-04 投放**：作为投放，我希望用种子人群做 Lookalike 扩量 100 万投放到巨量引擎，以便获取新客。
- **US-05 合规官**：作为合规官，我希望所有 PII 导出都走二次审批并留痕，以便满足监管检查。

## 7. 场景用例（Use Case）

### UC-01 高意向到店邀约
1. 系统每日 06:00 更新 L5 高意向人群至 Redis。
2. 旅程"L5_到店邀约_V3"启动，首先 SMS A/B 发券。
3. 24h 未到店 → 企微 1v1 跟进。
4. 48h 仍未到店 → 派单给 SDR 外呼。
5. 回收到店/成交结果 → 归因 → 模型迭代。

### UC-02 新车上市种草
1. 投放 BU 导入新车目标画像作为种子。
2. 系统做 Lookalike 扩量 500 万。
3. 推送至巨量引擎、腾讯广告 DMP。
4. 回传曝光/点击/留资。
5. 对留资用户走高意向旅程。

## 8. 约束与假设

- 公司已拥有阿里云/火山云账号与对象存储。
- 现有 CRM 支持 MySQL Binlog 开启。
- SDR 外呼系统有 OpenAPI 对接能力。
- 短信/企微/广告 DMP 由第三方供应商提供。
- 用户同意数据使用（授权存证由法务与业务共同保障）。

## 9. 验收标准（Acceptance）

- 全部 P0 功能通过 UAT。
- 非功能指标在压测环境达标。
- 合规审计（PII、权限、审计日志）通过内审。
- 第 1 期上线后 2 周内，运营方可独立完成"圈人 → 触达 → 看结果"全链路。

## 10. 变更管理

- 需求变更需提交 CR（Change Request），由 PM、架构师、QA 评审。
- 影响 P0 范围的变更须经业务负责人签字。
- 所有变更记录归档于项目管理文档。
