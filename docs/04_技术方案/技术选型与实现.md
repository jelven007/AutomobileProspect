## 2. 关键实现方案

### 2.1 OneID 合并算法

**强规则（直连）**：
- 手机号 MD5 一致 → 立即合并。
- 身份证哈希一致 → 立即合并。

**弱规则（概率）**：
- 特征：设备 ID、IP 段、UA、时间窗、行为相似度。
- 用 GBDT 预测合并概率，阈值 0.85。
- 结果写入 Nebula，边类型 `same_person`，带 `weight` 和 `rule_id`。

**冲突处理**：
- 保留最近活跃 OneID 为主 ID，其余为别名。
- 合并事件广播到 Kafka Topic `oneid_merged`。

### 2.2 亿级 Bitmap 圈选

**模型设计**：
```sql
CREATE TABLE user_tag_bitmap (
    tag_id       INT,
    tag_value    VARCHAR(64),
    user_bitmap  BITMAP BITMAP_UNION
)
AGGREGATE KEY(tag_id, tag_value)
DISTRIBUTED BY HASH(tag_id) BUCKETS 32;
```

**圈选 SQL 示例**：
```sql
SELECT bitmap_count(
    bitmap_and(
        (SELECT user_bitmap FROM user_tag_bitmap WHERE tag_id=1 AND tag_value='L5'),
        (SELECT user_bitmap FROM user_tag_bitmap WHERE tag_id=2 AND tag_value='一线'),
        bitmap_and_not(
            (SELECT user_bitmap FROM user_tag_bitmap WHERE tag_id=3 AND tag_value='留资_30d'),
            (SELECT user_bitmap FROM user_tag_bitmap WHERE tag_id=99 AND tag_value='opted_out')
        )
    )
) AS cnt;
```

**优化手段**：
- 热门人群结果缓存（Redis，TTL 15 分钟）。
- 高频组合物化视图。
- OneID 转 int64：维护 OneID ↔ int64 映射表。

### 2.3 画像点查

- HBase Rowkey = `md5(oneid)[0:4]_oneid`，避免热点。
- Column Family：`b`（basic）、`t`（tags）、`s`（score）、`e`（recent events）。
- Redis 二级缓存：Key = `profile:{oneid}`，Value = Pb 序列化，TTL 1h。
- 读路径：Redis → HBase → 回填 Redis。
- 写路径：Spark/Flink 直写 HBase，TTL 由 ColumnFamily 控制。

### 2.4 实时特征与打分

- Flink 消费 Kafka 事件 → 滑动窗口聚合（1min、5min、30min、1d、7d、30d）。
- 结果写 Redis：`feat:{oneid}:{feature_name}`。
- 打分服务读 Redis + HBase 组合特征 → Triton 推理 → 返回分数。
- 缓存：Redis `score:{oneid}` TTL 15min；高意向用户 TTL 更短。

### 2.5 旅程调度

- DAG 持久化到 MySQL。
- 调度器：时间轮（Netty HashedWheelTimer）+ Redis Zset 延迟队列。
- 并发：按 journey_id 分片到 N 个 Worker，Worker 内异步执行。
- 失败重试：指数退避（1s / 10s / 1min / 10min），超过 3 次进死信。
- 状态机：Pending → Running → Completed / Failed / Cancelled。

### 2.6 触达频控

- Redis Lua 原子操作：令牌桶 + 滑动窗口。
- 维度：`oneid × channel × 7d`、`oneid × 24h`、`campaign × hour`。
- 优先级：L5 > L4 > L3 > ...；超额时低优先级让位。

### 2.7 A/B 实验分流

- 一致性哈希：`hash(oneid + experiment_id) % 100`。
- 分层设计：同一用户在多个独立实验中可同时分流。
- 结果：事件带 `experiment_id`、`variant` 写入 Kafka，离线对齐。

### 2.8 归因（MTA）

- 口径：以成交事件为锚点，回溯窗口 90 天内所有触点。
- 模型：
  - Last Touch（基线）
  - Linear
  - Time Decay（半衰期 7 天）
  - Shapley Value（计算昂贵，用户采样 10%）
- 结果：每个触点贡献度 `[0,1]`，汇总到渠道/旅程/创意维度。

## 3. 性能方案

| 目标 | 手段 |
|---|---|
| 圈选 P95 ≤ 3s | Bitmap + 物化视图 + 结果缓存 |
| 画像 P99 ≤ 50ms | Redis + HBase 二级缓存 |
| 实时打分 P99 ≤ 100ms | Flink 特征预计算 + Triton GPU |
| 消息 50 万 QPS | Kafka 128 分区 + 批量生产 |
| 导出亿级名单 ≤ 10 min | 并行写对象存储 + 分片 Redis |

- 旅程：模拟 1000 万用户并发进入旅程。

## 5. 安全与合规实现

- **传输**：所有服务 TLS 1.3；内部 mTLS。
- **存储**：对象存储 SSE-KMS；HBase 字段级加密；手机号/身份证 **仅存哈希**，明文需走审批。
- **密钥**：KMS 托管；密钥季度轮换；密钥访问日志。
- **PII 处理**：
  - 字段级权限：销售只能看脱敏后 `138****1234`。
  - 导出必须二次审批 + 水印。
  - 导出 PII 自动加密压缩包。
- **退订**：全局 opt-out 位图，触达前强制查。
- **审计**：所有涉及 PII、人群导出、权限变更的动作入审计表（180 天）。
- **合规证据链**：数据来源、用户同意记录、使用用途、留存周期可追溯。

## 6. 可观测方案

- **指标**：
  - 服务层：QPS、RT P50/P95/P99、Error Rate、GC；
  - 数据层：ETL 成功率、滞后、数据量波动；
  - 模型层：AUC、KS、PSI、线上线下差异；
  - 业务层：圈选次数、触达量、到店率、ROI。
- **日志**：
  - 结构化 JSON，字段固定（trace_id、user_id、request_id）；
  - PII 自动脱敏；
  - Loki/ELK 聚合。
- **Trace**：OpenTelemetry + Jaeger；跨服务 traceparent 透传。
- **告警分级**：
  - P0（电话）：核心服务宕机、数据断流 > 15min；
  - P1（企微）：延迟超阈值、模型 AUC 骤降；
  - P2（邮件）：局部异常、低优指标。
